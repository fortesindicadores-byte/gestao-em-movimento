DriverPro — migração para o Git e o banco da Conlog

Roteiro para a TI Conlog · 08/10/2026 · origem: repositório fortesindicadores-byte/gestao-em-movimento (branch main). Acompanha o pacote DriverPro-migracao.zip.

Hoje o DriverPro roda fora da infraestrutura da Conlog: o código fica no GitHub (conta Fortes Indicadores), o banco é PostgreSQL no Supabase (projeto lozwipoeacpvplgkrxkq) e o site no GitHub Pages, com o domínio driverpro.onespot.com.br. Este documento diz o que cada peça é, de onde vêm os dados e como levar tudo para o Git e o banco da Conlog.

1. Como os dados chegam ao app

Geotab → robô de coleta → banco de dados → app do motorista e painel do gestor. Nada é digitado.

O que o robô lê do Geotab

ObjetoUso
User (motoristas)Nome e CPF. O CPF é o login do motorista no MyGeotab (campo name); só CPF com dígitos verificadores válidos é aceito. É com ele que o motorista entra no app.
Device, GroupPlaca e unidade (grupo do veículo, por exemplo EMP PIRAI)
TripKm, tempo dirigindo e tempo parado com motor ligado, por viagem e motorista
StatusData (DiagnosticEngineSpeedId)Amostras de rpm: tempo em movimento em cada faixa de giro
ExceptionEvent, RuleAcelerações bruscas (as freadas são gravadas, mas não pontuam)
FuelUsedLitros por viagem (km/L do painel; não entra na nota)

Viagem sem motorista identificado vai para um registro semlogin:<unidade>, que não é pessoa e não entra em ranking nem pagamento.

Regras vigentes que o sistema aplica

  • Nota 0–100 = 50% giro + 30% motor ligado sem rodar + 20% acelerações; dia → período ponderado por km.
  • Giro (régua Fabet): só a verde 1.000–1.400 rpm pontua; nota = verde ÷ (rodando − amarela 1.800–2.300 em descida ≤ −2%). Marcha lenta (≤ 900) fora da conta. A rampa sai do GPS (LogRecord) + relevo Copernicus DEM 30 m (npm geotiff@2.1.3; acesso de rede a copernicus-dem-30m.s3.amazonaws.com).
  • Carteira R$ 200, R$ 5 por ponto acima da nota 60 (ce_app_carteira, ce_app_regras.piso_nota). Todos que rodam 1.000 km recebem. Pódio R$ 300/150/100. Desempate por km.
  • Piloto só na unidade EMP PIRAI (ce_app_regras.unidades).
  • Período de apuração do dia 21 ao dia 20. A competência é o 1º dia do mês em que o período termina: 2026-12-01 = 21/11 a 20/12/2026 (1º período do piloto, pago na folha de janeiro/2027). No robô: compDe()/periodoDe(); no banco: ce_app_comp().
  • Pagamento: o sistema gera a lista (nome, CPF, valor); o RH lança na folha, na rubrica de prêmio, com o descritivo do programa no contracheque.

3. Passo a passo

  1. Repositório Git da Conlog: criar o repositório e subir app/, robo/, banco/ e workflows/. Se o orquestrador da Conlog não for o GitHub Actions, reproduzir o agendamento diário do robô.
  2. Banco: rodar banco/1-conducao-economica.sql e depois banco/2-app-motorista.sql (o segundo depende do primeiro). O app usa a API REST do Supabase (POST /rest/v1/rpc/<função>). Se o banco da Conlog não for Supabase, expor as funções ce_app_* por PostgREST. As políticas usam os papéis anon, authenticated e service_role.
  3. Dados: copiar o conteúdo das tabelas public.ce_* (comando na seção 4).
  4. Trocar os endereços fixos (hoje apontam para o Supabase atual):
    • app/index.html: SUPABASE_URL e SUPABASE_KEY (chave pública/anon);
    • robo/conducao-robot.mjs e robo/driverpro-check.mjs: SB_URL;
    • painel/conducao-economica.html: URL e chave do banco;
    • app/sw.js: subir o nome do CACHE a cada publicação (é o que faz o celular trocar de versão).
  5. Segredos do robô (variáveis de ambiente): GEM_SUPABASE_SERVICE_KEY (chave service_role do banco novo) · GEOTAB_USER · GEOTAB_PASS · GEOTAB_DB (ambev) · GEOTAB_SERVER (my.geotab.com) · VFLEETS_TOKEN (opcional, sem uso hoje). As credenciais não estão no pacote: o Renan passa por canal seguro.
  6. Agendamento: robô 1× por dia, de manhã, CE_MODE=ano. Leva poucos minutos por dia; depois de um buraco ele se recompõe sozinho.
  7. Site do app: publicar app/ como site estático com HTTPS e apontar o DNS de driverpro.<domínio> (hoje driverpro.onespot.com.br, DNS no Registro.br). É PWA: precisa de HTTPS e de servir index.html e sw.js com Cache-Control: no-cache.
  8. Conferência: node robo/driverpro-check.mjs contra o banco novo e login de teste no app (CPF de teste 00000000191, motorista sintético teste:driverpro).
  9. Virada: parar o robô antigo, rodar o novo, trocar o DNS. Se o domínio continuar o mesmo, os motoristas não reinstalam nada (só criam senha de novo se a tabela ce_app_acesso não for migrada).

4. Cópia dos dados

Estrutura e funções vêm dos .sql; dos dados basta o conteúdo das tabelas. Com a string de conexão do Supabase atual (Project Settings → Database, fornecida pelo Renan):

pg_dump "postgresql://postgres.lozwipoeacpvplgkrxkq:<SENHA>@<HOST>:5432/postgres" \
  --data-only --no-owner --no-privileges \
  -t public.ce_motoristas -t public.ce_diario -t public.ce_scores_mensais \
  -t public.ce_app_regras -t public.ce_app_unidade_cfg -t public.ce_app_admins \
  -t public.ce_app_acesso -t public.ce_app_sessao -t public.ce_app_log \
  > driverpro-dados.sql

psql "<conexão do banco novo>" -f driverpro-dados.sql
Os dados incluem nome e CPF dos motoristas e o hash da senha: tratar como dado pessoal (LGPD).

6. Observações

  • Painel do gestor: usa o login do portal Gestão em Movimento e scripts compartilhados (assets/). Pode ficar no portal lendo o banco novo (trocar URL e chave) ou ser refeito no BI da Conlog. Também lê ginfo_snapshot (base de ativos) para modelo e projeto da placa; sem essa tabela ele funciona, só sem essas duas colunas.
  • Funções duplicadas: ao rodar só um trecho de 2-app-motorista.sql, nunca levar a seção 7 sem o drop da versão antiga de ce_app_dados(uuid). Duas versões da função fazem a API recusar a chamada do motorista (HTTP 300).
  • Segurança: app e painel usam só a chave pública; as tabelas têm RLS e o app só vê o que as funções ce_app_* devolvem para o CPF logado. A chave de serviço fica só no robô.
  • O descritivo completo do programa (regras, LGPD, origem dos dados) segue em PDF à parte.
